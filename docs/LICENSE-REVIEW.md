# Quickhand POS 授权机制分析与兼容迁移

> 2026-11-25：厂商工具已拆分到本仓库的 `LicenseKeyGenerator.sln`。本文保留历史分析与验证记录；其中 `Seals`、`Common`、`InitializeShared` 及 `Scripts/Test-*License*.ps1` 路径属于 POS 仓库。当前独立工程的操作说明和路径以 [分离说明](分离说明.md) 为准。

## 第二阶段已实现：签名离线授权

本分支新增厂商签名授权、签发工具和后台授权管理入口，继续接受原有客户的旧授权。第三阶段的联网激活、服务端校验和部署没有开展。

### 客户端行为

- `Seals/Licensing` 校验版本 2 的离线 JSON 文件。RSA-3072、SHA-256、PKCS#1 v1.5 固定组合；只信任程序内嵌的厂商公钥，先验证原始 payload 字节的签名，再解释权限。拒绝未知公钥/版本/产品、重复字段、未知字段、无效日期、超大文件和错误机器。
- 新授权明确区分永久 POS、限期 POS/试用、APP、Web 和支付权益。APP、Web、支付到期不会使永久 POS 到期；支付额度独立校验。所有新日期使用 UTC，旧日期保留原本地时间语义。
- 新安装编号由原硬件摘要与 Windows MachineGuid 共同派生，不把原始硬件序列号写进请求。两个值严格绑定；这不是可随意复制到另一台机器的账号，也不是按磁盘任意更换容错。旧授权机器码算法没有变化。
- `Settings > Software license` 提供安装编号、导出请求、功能状态和导入授权。界面保留旧机器码，便于旧格式售后。导入要求设置修改权限；启动恢复窗口允许未登录时导入，但必须通过同样的文件验证。
- 蓝白触屏页面，正文至少 12pt、按钮 48px；1024×768（含边框和任务栏）、嵌入设置页及 18pt 字体已验证。签发工具的长表单滚动，确认、结果提示与底部操作保持可见。
- 导入失败不替换当前内存权限；写入状态失败回滚授权主文件。原文件保存在 `license.key.bak`，受保护的本地状态在 `license.key.v2state` 和其 `.bak`。
- 成功迁移后，现存状态阻止自动退回旧 DES 文件。相同授权编号不能倒退版本，不能用不同内容覆盖同一版本；替换另一授权编号必须有厂商签名的 `replacesLicenseId` 和原因。
- 本地状态使用 Windows DPAPI LocalMachine 加密，保存授权版本和最近观察时间；运行中每分钟保存一次，并用进程单调计时防止运行时调钟延长有效期。首次正常加载/导入即写状态。
- 限期 POS 到期或状态保存失败后，不能开始新的前台保存/结账；到期前已经进入的结账允许完成记录。新的终端收款会重新检查支付许可，已经确认的付款不因许可变化而撤回。旧授权业务行为保持原样。
- 主文件删除、签名失败或本地状态损坏都不会自动恢复旧权益。仅在用户显式导入同编号、更高版本且签发时间不早于备份最近时间的新授权时，才允许利用有效状态备份恢复损坏/丢失的状态。没有有效备份时停止自动恢复，交由售后处理。

APP 字段沿用现有兼容接口；本阶段没有重新启用已移除的旧手机 AppServer。Web 权限在现有客户端入口检查，本阶段没有给独立网络服务增加在线授权或即时吊销机制。

### 厂商首次配置（只需做一次）

**本提交没有生成真实厂商私钥，内嵌公钥列表初始为空。** 旧授权可以照常使用；要给客户启用签名授权，先完成以下步骤。测试使用临时密钥，不会把测试密钥变成生产信任。

1. 在厂商电脑运行 `LicenseGenerator.exe`，默认进入新签发界面。输入至少 16 字符的密码，点击 `New key`，保存到代码仓库外的受控目录，例如 `D:\Quickhand-Vendor-Licensing\license-signing.pfx`。生成器拒绝把私钥、签发文件和签发记录放入任何 Git 工作区。
2. 安全备份 `.pfx`、密码及同目录的 `license-issuance.jsonl`，不要把它们放进客户安装目录、Git 或升级包。生成器也会输出 `.pfx.public.json`，其中只有公钥。
3. 在源码根目录用 Windows PowerShell 导入公钥：

   ```powershell
   .\Scripts\licensing\Add-TrustedLicenseKey.ps1 -PublicKeyFile 'D:\Quickhand-Vendor-Licensing\license-signing.pfx.public.json'
   ```

4. 脚本验证公钥类型、长度和编号，修改 `Seals/Licensing/TrustedLicenseKeys.json`；重复执行不会重复添加。提交这个仅含公钥的改动，重新编译并通过 `Scripts/release/Build-Release.ps1` 发布全部关联程序集。先让客户安装含该公钥的版本，再导入用对应私钥签发的授权。
5. 授权签名密钥与软件升级包签名密钥分开。轮换时将新公钥加入列表、发布客户端，再用新私钥签发；旧公钥保留到旧授权完成迁移。所有轮换密钥应使用同一受控目录和同一份签发记录，不能以换目录/清空记录来重用版本号。

公钥无需隐藏。客户不能凭公钥签发授权；私钥与密码才是需要保护的签发材料。密码不写入配置或审计文件，签发用的 PFX 不永久导入 Windows 证书存储。请限制厂商文件夹的 Windows 访问权限并妥善管理备份。

### 日常签发、续期和换机

1. 客户在 `Software license` 点击 `Export request`，把请求文件交给厂商；请求中不包含购买权益。
2. 厂商 `Load request`，填写客户/门店、各功能权限、期限和支付终端数量；选择 PFX 并输入密码。默认永久 POS，其他功能默认关闭，不能依据一个旧文件自动授予额外权限。
3. 核对客户购买记录，勾选确认后 `Issue license`。输出 `.qhlic` 文件并记录操作人、授权编号、版本、时间、机器摘要、替换原因和文件摘要。只把 `.qhlic` 发给客户。
4. 客户 `Import license`。成功后，待当前营业操作结束，再重启 POS/MenuTool，使各进程和已有功能窗口加载一致状态。原授权仍在其他进程中使用时，它们会发现状态变更并要求刷新，而不会自动读取外部未验证权限。
5. 续期：请求自动带出当前授权编号和版本，生成器建议版本加一。必须同时核对厂商记录，以厂商已经签发/预留的最高版本为准；重复签发同一版本会被拒绝。先写审计后发布文件，异常中断可能占用一个版本号，使用下一个版本重签即可。
6. 换机：在新机器导出请求；厂商输入原授权编号、更高版本和换机原因。新文件只能在目标机器使用。新硬件没有原购买记录，须人工核对，不能凭安装编号自助换机。
7. 改用全新授权编号时，填写原编号到 `Replace ID` 并提供原因；普通续期保持原编号。状态恢复续期必须保持原编号，不能以新编号跳过备份校验。
8. `Legacy` 按钮或 `LicenseGenerator.exe --legacy` 可进入原生成器，为尚未迁移的客户处理旧格式授权。已成功迁移的安装不能用这个入口退回旧授权。

离线换机**不会即时吊销旧机器上已经有效的旧文件**。永久离线授权、管理员删除/恢复所有状态、磁盘或系统镜像克隆、客户端被修改和机器时间来源都不能仅靠本地文件彻底控制。本地时钟不是服务端可信时间；分钟级落盘也不能承诺断电零时间回退。联网激活/吊销属于未实施的第三阶段。

## 当前流程

1. `KeyGenerator` 显示并复制硬件编号；`LicenseGenerator` 也能读取本机编号，人工填入客户信息、功能和期限。
2. `Seals/Locker.cs` 生成硬件编号和产品码；`Common/Share/Utility.cs::GetXMLFileContent` 生成 XML；生成器加密后直接写入其启动目录的 `license.key`。
3. POS 的 `GlobalSettings.ReadBasicSettings` 调用 `ReadLicenseInfo`，解密并读入静态 `Seals.License`，必要时扣减试用次数并写回文件。
4. `ApplicationStartupInitilization.ValidateLicense` 另外读取 `CDK.dat`，随后比较当前硬件对应产品码。`SmartPOS/Program.cs:156` 和 `ManagerTool/Program.cs:76` 都调用这个检查，调用点没有排除 Debug。
5. 支付功能还检查激活标志、支付到期时间和允许终端数。`GetPaymentLicensed` 被结账和订单报表使用，读取支付配置时另有终端数量检查。

相关入口：`Seals/Locker.cs`、`LicenseGenerator/License.cs`、`Common/Share/GlobalSettings.cs:691`、`InitializeShared/Share/ApplicationStartupInitilization.cs:187`。

## 加密和机器绑定细节

| 部分 | 实现 | 影响 |
| --- | --- | --- |
| 文件内容 | XML 包含产品码、试用次数、APP 权限和期限、设备编号、Web 标志、支付权限和期限、终端数 | 权限和可变运行状态混在一个文件 |
| 加密 | `DESCryptoServiceProvider` 默认 CBC、PKCS7；固定 IV，程序内固定密码；UTF-8 明文加密后 Base64 | 相同内容产生相同密文；Base64 只是编码；没有独立签名或 MAC 校验 |
| 密钥 | 加密函数取密码前 8 个字符的 UTF-8 字节；DES 有效密钥长度为 56 位 | 固定密钥分发给所有客户端，更新成更长的对称密钥也无法解决客户端可签发问题 |
| 解密 | 使用整个密码的 UTF-8 字节 | 与加密截取规则不一致；当前固定 ASCII 密码恰好能匹配，通用调用不可靠 |
| 产品码 | 对硬件编号和固定盐进行两次 MD5 派生 | 客户端和生成器具备同一派生能力，不是数字签名 |
| 硬件编号 | 主板序列号与系统磁盘序列号拼接，MD5 大写后取前 16 个十六进制字符 | 64 位截断标识；换主板或硬盘可能改变；既不是加密，也不是可信设备证明 |

主板读取函数叫 `GetBiosInfo`，实际查询 `Win32_BaseBoard.SerialNumber`；磁盘通过系统盘关联找到物理盘序列号。硬件读取失败的回退字段没有赋值，两项都失败时可能对空字符串生成同一编号。OEM 通用序列号也可能重复，应明确识别“取不到有效标识”，不能当成一台正常机器。硬件编号在进程内缓存，进程重启前不会重新计算。

DES 标准已被 NIST 撤销；更根本的问题是客户端持有签发所需材料。更换 AES、增加混淆或隐藏字符串只能增加分析成本，不能替代非对称签名。[NIST DES 标准状态](https://csrc.nist.gov/pubs/fips/46-3/final)

## 已确认的问题及处理顺序

| 优先级 | 位置和问题 | 建议 |
| --- | --- | --- |
| 高 | `Seals/Locker.cs::EncryptDES` 捕获异常后返回原始明文；生成器仅检查非空就写文件 | 加密或签名失败必须返回明确失败，禁止写出半成品或明文 |
| 高 | 同文件 `DecryptDES` 失败调用 `Environment.Exit(1)` | 库返回验证结果，让界面显示损坏、错误机器或过期等原因，并提供重新导入入口 |
| 高 | `ValidateLicense` 对 `CDK.dat` 使用 `BinaryFormatter.Deserialize`；得到的 `key` 没有参加后续比较，但文件缺失或损坏仍阻止启动 | 移除这条冗余依赖；如必须兼容旧格式，采用受限迁移过程，不能继续通用反序列化本地可写文件 |
| 高 | `LicenseGenerator/License.cs:62` 把 `Seals.License.PaymentTerminalsAmount` 当作试用次数，静态默认值为 0 | 将试用次数或期限明确建模，不得从终端数量取值；当前新生成试用文件可能立即到期 |
| 高 | `ReadLicenseInfo` 中空产品码且次数大于默认上限 30 时没有拒绝；次数和付费状态分支混杂 | 严格校验类型、上下限和授权类别；签名通过后再解释权限 |
| 高 | 授权文件可复制回旧版本以回退试用计数 | 将不可变的签名授权与本地使用状态分开；需要可靠防回退时结合服务端状态，离线状态不能承诺绝对防篡改 |
| 中 | `m_txtAppFactor` 被要求非空，但实际产品码计算未使用它；`GetLicenseCode(hash, factor)` 是另一个未使用的帮助方法 | 删除没有业务作用的输入，避免操作员以为它决定授权安全性 |
| 中 | `SoftwareSettingDetail` 用到期年份与当前年份比较 | 使用完整时间比较；同年已过期不能显示仍有效 |
| 中 | 先把解密字段赋给全局静态对象，再继续检查 | 解析到临时模型，全部校验成功后一次性替换当前授权，失败不能留下部分新权限 |
| 中 | 试用读写在加载设置时发生，重复初始化可能重复扣次数 | 给“启动一次”明确边界；优先采用清晰的期限型试用，期限属于业务决定 |
| 中 | 运行时原子写使用进程内锁和固定 `.tmp` | 如保留可变状态，使用跨进程协调和唯一临时文件，避免 POS 与管理工具同时写入 |

`BinaryFormatter` 的问题发生在转换为 `byte[]` 之前，事后强制转换不能限制反序列化过程中执行的行为。[Microsoft 安全说明](https://learn.microsoft.com/en-us/dotnet/standard/serialization/binaryformatter-security-guide)

目前文件保存已有值得保留的处理：原子替换、写入刷新、备份，以及“主文件被删除时不能自动从备份恢复授权”。只有主文件存在但为空时恢复备份；非空损坏内容没有同样的恢复路径。备份应先验证签名和机器条件，绝不能通过恢复旧授权绕过撤销、降级或用户主动删除。

## 容易误解的权限和旧逻辑

`app@expirydate` 是 APP 功能字段；主 POS 硬件验证没有把它当作整个 POS 的到期时间。不能直接把这个日期用于禁止收银，否则可能改变既有合同。支付授权有自己的期限和终端数量。新结构应明确 `pos`、`payment` 等功能各自的期限，永久授权用明确的永久标志，不能靠某个特别大的日期表示。

`Login.VerifyLicenseOnServerSide` 定义了在线检查，但在检查到的 POS、管理工具和共享界面代码中没有调用点。该方法还有 `(numbers++).ToString()` 保存旧计数的问题；其登录记录请求遇到空响应返回的值也可能被当作成功。应作为待清理的旧逻辑，不能据此宣称当前软件已有可靠在线吊销。

`ValidateLicenseNew` 直接返回 `true`，也没有发现调用点；`ParseProductCode` 可以从设置读取产品码，但没有发现有效调用点。建议删除这些会误导维护者的旧入口，集中到一个授权服务。`Common/Share/MapApi.cs` 还把产品码作为服务 API 参数；后续应分离授权编号和服务访问凭据，不让长期授权码兼任网络密码。

## 推荐方案

保留离线营业能力，使用一个版本化的签名授权文件。厂商系统保管私钥并签发，POS 仅安装公钥并验证。文件内容可以是可读的 JSON：授权安全依赖签名，通常不需要再加密客户名和功能列表；也应避免把原始硬件序列号放入文件。

建议先用 .NET Framework 4.8 可实现的 RSA 3072 位、SHA-256 和明确固定的签名填充方式。接口固定为签名、验签、解析三层，不自行设计密码算法。RSA 验签是框架已有能力，不要求把 POS 升级到 .NET 9。[RSA.VerifyData 文档](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.rsa.verifydata?view=netframework-4.8.1)

| 授权字段 | 用途 |
| --- | --- |
| schemaVersion、keyId | 识别格式和厂商公钥版本，支持换钥匙 |
| licenseId、customerId、storeId | 稳定的售后、审计和门店关联编号 |
| installationId、deviceBinding | 区分安装实例和机器绑定；安装编号可复制，不能单独证明机器身份 |
| issuedAt、notBefore、expiresAt | UTC 时间，明确生效和到期边界；永久授权单独表达 |
| product、edition、features | POS、支付、Web 等权限和各自期限 |
| paymentTerminals | 非负且有明确上限的支付终端配额 |

文件外层仅保存版本、公钥编号、原始 payload 字节的 Base64 和签名。签名覆盖原始 payload 字节，验签成功后才解析，避免不同 JSON 序列化顺序产生歧义。限制文件大小、字段范围和嵌套深度，拒绝重复字段、未知算法、未知公钥、错误产品和无效日期。不要根据文件指定的任意算法动态选择验证方式。

公钥可以随安装包发布；私钥应只存在于受控签发端或密钥管理设备，不进入 POS、Git、安装包和常规构建产物。授权签名与软件升级包签名使用不同密钥，分别轮换和审计。新密钥先随客户端发布，再开始签发；旧公钥保留到对应授权结束或完成重签。

机器绑定建议允许经过审批的换机：采集多个可用、稳定的标识，保存摘要，按明确的容错规则验证。不能笼统要求“任意两个相同就通过”，必须验证标识有效性和碰撞/克隆风险。硬件全失效时给出可恢复错误，由厂商重新绑定。离线客户端处在客户机器上，无法承诺完全防破解或即时吊销；需要即时控制的功能应依赖服务端授权。

## 更简单的客户操作

1. POS 首次打开“软件授权”，显示安装编号，支持复制和导出请求文件；不再要求客户理解 Hash、Factor 或 CDK。
2. 厂商选择客户、门店、购买功能和期限，签发一个授权文件。签发工具记录操作人、时间、换机原因和前一个授权编号。
3. 客户点击“导入授权”，POS 验证签名、机器、产品和期限。成功后原子替换；失败保留现有可用授权，并直接说明原因。
4. 续期导入新文件，沿用安装编号。换机走厂商重新绑定，不让员工自行复制授权解决问题。
5. 有服务器后增加一次性激活码：兑换后下载同一格式的签名文件。日常营业仍可离线，联网校验频率和宽限期由合同规则决定。

触屏页面沿用蓝白风格、正文不小于 12pt、按钮至少 44px，适配 1024×768。只显示“有效、即将到期、已到期、需要重新绑定”等业务状态，技术诊断放入详情。运行状态单独保存，并记录最近可信时间；系统时钟回拨给予明确提示和受控恢复，不能靠本机时间实现绝对可靠的离线期限控制。

## 迁移顺序和验收

先列清当前客户权益，再增加独立验证服务、签发工具和授权导入页面。过渡版本同时识别旧、新文件；旧文件按旧规则运行，新文件只接受有效签名。不能仅凭一个可被本地修改的旧文件自动签发更高权限的新授权，厂商应按客户记录确认。新授权成功导入后才切换验证路径，卸载升级不得删除客户授权；升级程序继续保留现有 `license.key`。

后续移除 CDK 和旧 DES 路径应有明确版本与迁移覆盖率，避免尚未换证的离线门店无法启动。授权变更应能审计和恢复，但恢复不能静默增加权限。

验收需覆盖逐字段篡改、错误签名/公钥、未知版本、重复字段、超大文件、过期边界、时区变化、时钟回拨、断网、磁盘更换、WMI 失败、重复硬件编号、多进程写入、突然断电、文件删除和备份恢复。还需确认永久 POS 权益不会因为 APP 或支付到期被意外取消。

最初分析时，`Scripts/Test-LicenseFile.ps1` 的 12 组文件读写回归通过，使用隔离临时文件和原工作区 Debug 程序集，没有修改真实授权。它验证删除、空文件恢复、原子保存等行为；第二阶段另增加 `Test-SignedLicense.ps1` 验证签名及迁移安全边界。

## 授权工具界面操作

独立版默认入口为 `LicenseKeyGenerator.exe`，仅由厂商使用，不进入客户安装包。界面分为 Generate license（日常签发）和 First-time setup（首次设置），无需手动运行公钥配置或构建命令。

首次设置：

1. 在 Key password 输入密钥密码；使用现有 PFX 时不需要填写确认密码。点击 Use existing key 选取已有 PFX。若原文件在 Git 源码目录内，界面要求选择一个仓库之外的空目录，复制密钥及同目录签发记录；保留原文件，不覆盖其他密钥或合并签发记录。今后统一使用新目录，不在旧副本上签发。
2. 没有密钥时，填写至少 16 字符的密码及确认密码，点击 Create new key，保存到仓库以外。备份 PFX、密码和 `license-issuance.jsonl`；不要为每个客户创建新密钥。
3. Choose source 选择源码根目录，点击 Configure POS key。工具从解锁的 PFX 导出并验证公钥，原子追加到源码的受信任列表，保留旧公钥；不会把私钥放进客户端。
4. Build local POS 编译本地 Debug POS 和 MenuTool；先关闭相关程序、停止 VS 调试。给客户分发时使用 Build installer：选择版本、catering/common、测试或正式发布，然后 Start build。它调用现有 `Build-Release.ps1`，按所选正式/测试发布目录自动决定是否创建基准，保留既有验证、归档和提交要求，不执行安装。
5. 安装包的 XML 更新签名密钥与 PFX 授权密钥分开选择；不填 XML 私钥时不会产生签名离线更新元数据。已有发布线的公钥会沿用，缺失或损坏的历史不能绕过发布脚本检查。密钥轮换仍须先给客户部署含新公钥的程序。

构建窗口的 Inno compiler 会自动查找 Inno Setup 6/7，包括 32 位工具启动时的 64 位安装目录、注册表中的自定义安装目录和 PATH。未找到时，点击 Choose ISCC.exe... 选择安装目录中的 `ISCC.exe`（不是打开编辑器的 `Compil32.exe`）。选择会记忆在当前 Windows 用户的 `LocalAppData/QuickhandPOS/LicenseIssuer/build-tools.json`，仅保存路径，无需输入命令。Start build 会先确认编译器存在，再启动构建并把该路径传给发布脚本，避免跑完检查后才发现找不到编译器。

日常签发：

1. 客户在 POS 中 Export request，将 JSON 申请文件发给厂商。
2. Generate license 中 Load request；申请文件不得作为 PFX 使用。工具自动填写授权 ID，结合申请和本机签发记录确定下一修订号；切换客户申请会清除前一个客户的功能选择和编号输入。
3. 输入 Customer ID、Store ID、密钥密码，选择已购功能，核对后勾选确认，点击 Generate license。
4. 仅将生成的 `.qhlic` 发给客户；客户 Import license 后结束营业并重启相关程序。
5. Advanced 提供换机、替换授权 ID、修订号、APP 限制等少用选项；换机仍需按客户记录批准并填写理由。Legacy 保留旧授权工具入口。

工具只在厂商 Windows 用户的本地设置中记忆密钥、源码和输出目录，密码仅保留在本次窗口内。仓库下的 `QuickhandLicenseKeys` 目录整体忽略，避免密码文本等辅助文件被误提交；已有文件不自动删除。

新增验证覆盖公钥重复配置与轮换、私钥拒绝、原签发记录迁移、修订号保留、无密码的路径记忆、正式/测试基准隔离、真实界面启动模拟发布脚本及错误日志显示，以及 1024×768 下两页操作按钮的祖先容器裁剪检查。模拟发布测试不替代完整发布流水线或安装验收。
